# ADR 015: スキャン偽陽性の防止

## Status

Accepted

## Context

`shiori update` を実行すると、registry.json にゴミエントリが生成される問題が発見された。原因は3つに分類される。

### 原因1: テストファイルがスキャン対象に含まれている

デフォルトのスキャンパターン (`**/*.{css,scss,pcss,js,ts,tsx,jsx}`) は `tests/` ディレクトリを除外しない。テストコードは文字列リテラルとしてアノテーション例を含むため、実際のアノテーションと区別できない:

```typescript
// tests/comment-provider.test.ts
const input = makeInput('// shiori:SUP-1234');
//                        ^^^^^^^^^^^^^^^^^ 文字列リテラル内だが、行の // がコメントとして検出される
```

結果: `SUP-1234');`, `ignore');`, `JIRA:PROJ-123');` などの ref が生成される。

### 原因2: 行ベースの正規表現がコメントと文字列リテラルを区別できない

CommentProvider の `extractComments()` は `LINE_COMMENT_RE = /\/\/.*/g` で行コメントを検出する。この正規表現は文字列リテラル内の `//` にもマッチし、引用符・括弧・セミコロンを含む文字列がそのまま ref として抽出される。

### 原因3: JSDoc/ドキュメントコメント内の `shiori:` 言及

ソースコード内の説明的なコメントが `shiori:` をコンセプトとして言及している場合、パーサーはそれを実際のアノテーションとして解釈する:

```typescript
/** Whether the annotation has an explicit `shiori:` marker in source */
// → ref: "`", "marker" が生成される

// Path B: standalone shiori: (no matcher matched)
// → ref: "(no" が生成される
```

### 実際に生成されたゴミエントリ

| ref                                        | 原因    | 発生源                                             |
| ------------------------------------------ | ------- | -------------------------------------------------- |
| `(no`, `)`, `/`, `` ` ``, `→`              | 原因3   | ソースコード内の説明コメント                       |
| `ignore');`, `JIRA:PROJ-123');`            | 原因1+2 | テストファイルの文字列リテラル                     |
| `SUP-1234',`, `SUP-1234');`, `SUP-BIOME',` | 原因1+2 | テストファイルの文字列リテラル                     |
| `marker`, `marker)`, `prefix`              | 原因3   | JSDoc/コメント内の概念的言及                       |
| expires: `"2026-06',"`                     | 原因1+2 | テストファイルの文字列リテラル（値にJS構文が混入） |

## Decision

### 段階的アプローチ: A + B + D + F

AST ベースのコメント抽出（後述のアプローチ C）は全対応言語のパーサーが必要で、ADR 001 の「言語非依存の外部 CLI」という設計思想とコスト面から v0.0.1 では採用しない。代わりに4つの低〜中コストの対策を組み合わせる。

### A. デフォルト除外パターンの拡充

テストファイル・設定ディレクトリをデフォルトの除外対象に追加する:

```typescript
const DEFAULT_IGNORE = [
  // 既存
  '**/node_modules/**',
  '**/dist/**',
  '**/.git/**',
  // 追加: テストファイル
  '**/tests/**',
  '**/test/**',
  '**/__tests__/**',
  '**/*.test.*',
  '**/*.spec.*',
  // 追加: 設定ディレクトリ
  '**/.config/**',
];
```

**設計判断**:

- lint disable のテストファイルでは多数の `shiori:` リテラルが出現するため、偽陽性の主要な発生源を断つ
- shiori の設定ディレクトリ（registry.json 等）がスキャン対象になるのも防ぐ
- 既存の `config.yaml` の `scan.ignore` でユーザーがオーバーライド可能。テストファイルをスキャンしたい場合は除外パターンを上書きできる

### B. ref バリデーションの追加

registry 生成層で ref の妥当性を検証し、不正な ref をフィルタリングする。

**バリデーション規則**:

```typescript
const REF_PATTERN = /^[A-Z][A-Z0-9]*(?:[-:][A-Za-z0-9][-A-Za-z0-9._]*)*$/;
```

許可される ref の例: `SUP-1234`, `ADR:0007`, `JIRA:PROJ-123`, `DEV-001`, `MIG-1`
拒否される ref の例: `prefix`, `marker`, `');`, `` ` ``, `→`, `(no`

**配置の設計判断**:

バリデーションは `parseShioriFields()`（パーサー）ではなく、`initRegistry()`（registry 生成層）で行う。

- パーサーは入力を忠実にパースする責務に留める。何が「有効な ref」かはアプリケーション層のポリシー
- 将来、ref フォーマットの制約を緩和・変更する場合にパーサーへの影響がない
- `verify` コマンドに `ref-format` 警告を追加することで、ユーザーに不正な ref を通知できる

### D. ソースコメントの書き換え

shiori 自身のソースコード内で `shiori:` をコンセプトとして言及しているコメントを、パーサーが検出しない形式に書き換える:

- JSDoc 内の `` `shiori:` `` → アノテーション検出を回避する表現に変更
- Path 説明コメント内の `shiori:` → 同上

これは shiori 自身の dogfooding（自身のソースをスキャンする運用）で必要な対策である。一般ユーザーのプロジェクトでは通常発生しない。

### F. `update --dry-run` フラグの追加

`update` コマンドに `--dry-run` フラグを追加し、registry への書き込みを行わずに新規 ref のプレビューのみ表示する。

- 既存の実装で `newRefs` は計算・表示済み（update-cli.ts）のため、`saveRegistry()` の前で処理を停止するだけで実装可能
- ユーザーが registry 更新前にゴミエントリの混入を確認できる安全弁

## Alternatives Considered

### C. AST ベースのコメント抽出

`extractComments()` を言語ごとの AST パーサーに置き換え、文字列リテラルとコメントを正確に区別する。

- **利点**: 文字列リテラル内の `//` を完全に排除。URL やテンプレートリテラルの偽陽性も解消
- **欠点**: 対応言語（JS, TS, TSX, JSX, CSS, SCSS, PCSS）ごとにパーサーが必要。依存関係が大幅に増加し、ADR 001 の言語非依存方針と緊張関係を生む
- **判断**: v0.0.1 では不採用。A+B で偽陽性の大部分を排除した後、本番コードでの偽陽性が問題になった時点で検討する。中間案として「引用符を認識する簡易抽出器」（フル AST 不要）も将来の選択肢

### E. JSDoc ヒューリスティック

`/**` で始まるブロックコメント内の `shiori:` は、行頭でない限りスキップする。

- **利点**: ドキュメントコメントからの偽陽性を抑制
- **欠点**: ヒューリスティックが脆弱。意図的に JSDoc 内に書いた `shiori:` アノテーションを見逃す可能性
- **判断**: D（コメント書き換え）と B（ref バリデーション）で十分対処可能。ヒューリスティックの複雑さに見合わない

### ref バリデーションをパーサー層に配置

`parseShioriFields()` で ref フォーマットを検証する。

- **欠点**: パーサーの責務が拡大する。ref フォーマットのポリシーは利用コンテキストによって異なる可能性がある
- **判断**: B で述べた通り、registry 生成層/verify 層に配置する方が責務分離として適切

## Consequences

### 変更されるもの

- `DEFAULT_IGNORE` パターンの拡充（scan-cli.ts）
- `initRegistry()` に ref バリデーションの追加（registry-generator.ts）
- `update` コマンドに `--dry-run` フラグの追加（update-cli.ts）
- shiori ソースコード内のコメント書き換え（CommentProvider.ts, types.ts 等）

### 追加されるもの

- `ref-format` verify 警告（verify.ts）— 不正な ref フォーマットをユーザーに通知

### 将来の拡張パス

- **v0.1 候補**: 引用符認識型の簡易コメント抽出器（フル AST 不要の中間解）
- **v0.2+ 候補**: 言語別 AST パーサーによる正確なコメント抽出（C）

### 他 ADR への影響

- **ADR 001**: 言語非依存の設計方針を維持。AST パーサーの導入は明示的に先送り
- **ADR 014**: `update` コマンドに `--dry-run` フラグが追加される
